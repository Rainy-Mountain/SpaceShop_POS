# 발표에서 설명할 핵심 코드

## 1. AI로 구현한 MVP를 검증하는 과정

발표에서는 **AI로 하루 안에 MVP를 구현한 과정**과 **핵심 로직을 검증·보강한 과정**을 나눠 설명하면 좋습니다.

> AI를 활용해 기능을 빠르게 구성한 뒤, 결제·재고·정산처럼 데이터가 틀리면 안 되는 부분을 따로 검토했습니다. 성공하는 화면만 확인하지 않고 중간 실패와 재시도를 테스트했고, 발견한 문제를 DB 트랜잭션과 결제 식별자로 보강했습니다.

## 2. 결제: 여러 HTTP 요청에서 하나의 트랜잭션으로

- 프런트 진입점: `src/lib/orderActions.ts`의 `completePosPayment`, `src/lib/inventoryActions.ts`의 `checkoutKioskCart`
- 공통 요청·검증: `src/lib/paymentActions.ts`
- 데이터 무결성: `supabase/migrations/20261016_core_integrity.sql`의 `complete_sale`, `void_sales`

이전에는 재고를 줄인 뒤 매출 저장이 실패하면 주문은 결제 완료인데 매출은 없는 상태가 가능했습니다. 변경 후에는 같은 DB 함수에서 처리하므로 어느 단계에서 실패해도 전체가 되돌아갑니다.

여러 계산대가 같은 상품을 판매할 때는 재고 행을 잠그고, 여러 상품의 잠금 순서를 상품 ID 기준으로 맞춥니다. 화면에 표시된 재고가 오래된 값이어도 최종 판단은 DB가 합니다.

중복 클릭을 막는 UI 잠금만으로는 응답 유실을 해결할 수 없습니다. 같은 결제 요청에는 같은 UUID를 사용하고 DB가 이미 처리한 요청인지 확인합니다. 재시도 ID는 세션에 보관하며 성공 확인 후 지웁니다. 주문 결제는 주문 UUID를 결제 ID로 사용합니다.

보여줄 테스트: 매출 INSERT 실패 → 재고·주문·대기열 모두 원상태, 같은 요청 두 번 → 매출 한 건, 취소 두 번 → 재고 복구 한 번.

## 3. 정산: 시간 추측 대신 결제 ID로 집계

- `src/lib/paymentIdentity.ts`: 피드와 PDF가 공유하는 결제 식별 규칙
- `src/lib/fetchAllRows.ts`: API의 페이지 제한을 넘는 데이터 조회
- `src/lib/buildSettlementReport.ts`: 정산용 집계

이전에는 같은 초에 발생한 서로 다른 결제를 한 건으로 셌습니다. 이제 명시적인 결제 ID를 기준으로 집계합니다. 매출 조회의 1,000행 제한도 제거하고 관련 주문 조회는 ID를 100개씩 나눠 요청합니다. 페이지 조회 실패를 매출 0원으로 숨기지 않습니다.

보여줄 테스트: 같은 초의 서로 다른 결제 두 건 → 두 건, 한 결제의 여러 품목 → 한 건, 1,001행 및 서버의 작은 페이지 제한 → 전체 행 반환.

행을 여러 페이지로 읽는 동안 다른 기기에서 취소·삭제가 일어나면 엄밀한 시점 일관성은 보장되지 않습니다. 회계 확정 정산이 필요하면 DB의 한 스냅샷에서 집계하는 전용 RPC와 정산 마감 기능을 다음 단계로 도입할 수 있습니다.

## 4. 대기열: 번호와 고객 식별을 구분

- `src/lib/queueActions.ts`
- SQL의 `register_queue`, `set_queue_number`

클라이언트의 `최대 순번 + 1` 요청을 DB의 순번 할당으로 옮겼습니다. 번호 발급을 잠금으로 직렬화하고 유일 인덱스로 중복을 방지합니다. 직원이 수동 변경한 번호도 고려합니다.

전화번호 뒷자리 네 자리는 고객의 고유 식별자가 아닙니다. 같은 기기의 무작위 토큰으로 이어하기를 판단하고, 뒷자리가 같은 다른 손님은 별도 대기열로 등록합니다. 다른 기기나 브라우저의 이어하기를 위한 인증 흐름은 별도 기능입니다.

## 5. 구현 범위와 검증 한계

- 검증: PGlite에서 실제 SQL 실행, 실패 주입, 중복 재시도, 취소, 집계 회귀 테스트, TypeScript 검사, Next.js 프로덕션 빌드.
- 별도 확인: 실제 PostgreSQL 다중 연결의 경쟁 상황, 운영 RLS와 관리자 인증, 주류 인식 API 보호.
- 남은 개선: 장바구니 동기화의 삭제·재삽입도 단일 트랜잭션으로 묶기, 정산 시점 스냅샷, 큰 화면 컴포넌트 분리, 전체 ESLint 구성.

실제 Supabase에는 SQL을 자동 적용하지 않습니다. 앱을 실행·시연하기 전에 README의 적용 순서를 따라야 합니다.
